## 1. What this game is

A first-person, 4-player co-op horror game. Players spawn in a central hub room. Around the hub are several lockable challenge rooms, each containing a self-contained mini-game/puzzle. When the required number of players enters a challenge room and confirms (see Section 8 for the exact mechanic, now decided), the door locks, trapping them inside until they solve the mini-game. Solving it unlocks the door and grants a reward. The run continues until all rooms are cleared.

While players are off solving challenge rooms, danger escalates in the hub — this is the core tension mechanic, implemented as the Hub Threat System (see Section 8).

Rooms and which mini-games appear are randomized per run, but the mini-games themselves are fixed, hand-built content — this is NOT a fully procedural dungeon generator. Think "shuffle which pre-built rooms appear and in what arrangement," not "generate geometry at runtime."

Art direction: painterly, hand-illustrated horror aesthetic. Reference mood: Little Nightmares / Bendy and the Ink Machine, not photorealistic horror. The precise, actionable spec below is derived directly from the three mood-board images in `docs/art-reference/` — follow it when building rooms, don't just aim for "warm and dark":

- **Lighting setup**: 2 practical light sources visible per room, not 1 — typically one overhead/ceiling fixture (bare bulb or simple bulb-in-shade) plus one secondary practical at a different height (wall sconce, desk/banker's lamp, or a dropped/handheld flashlight lying on the floor, lit). A third *implied* source is common too: an adjacent space glows warm through a door's window or the gap of an open door, even though that space isn't modeled/lit in view. Aim for "2 practicals + 1 implied glow through the door" per room, not a single point light.
- **Color temperature**: very warm tungsten/candlelight, roughly 2200–2700K — more saturated golden-amber than a typical "warm white" bulb. Lit highlights should read as distinctly gold/mustard-yellow, not pale yellow-white.
- **Contrast ratio**: extreme, tight falloff, no soft gradient. Each light's usable pool is small — roughly a 2–3 meter radius before dropping to near-total black — with almost no fill/bounce light. Shadowed areas should read as flat, near-zero-value black (no visible ambient occlusion detail), not a softly-lit dark grey. Ceilings and upper corners are consistently the darkest part of frame and should stay essentially unlit.
- **Color palette**: a two-zone palette, not a continuous gradient. Shadow/base materials (walls, ceiling, unlit furniture) sit in desaturated brown-grey-black, roughly 10–20% saturation. Lit highlight zones jump to roughly 60–70% saturation golden-amber/mustard. No cool hues anywhere — no blue moonlight, no green/teal fill; warm-only lighting is a hard rule for this look.
- **Prop/material types**: worn, distressed wood furniture — tall cabinets and dressers with 3–5 visible drawers, wide-plank worn wood flooring, old wood-paneled doors (often with a small multi-pane window). Recurring "creature/doll" props with visible glowing eyes (roughly 2–4 per room), displayed as trophies on top of or mounted above furniture. Chains, manacles/shackles, and leather straps are a recurring captivity motif — draped over furniture, coiled on the floor, or hanging from a doorway. Small floor clutter (books/ledgers, tins, hand tools, loose gadgets) clusters at the base of furniture rather than spreading evenly across the floor — keep the main floor path relatively clear for gameplay readability.
- **Composition**: the door is the compositional anchor, placed centrally or just off-center in the middle third of the frame, usually backlit or showing warm light through its window/gap. The key light is angled to rake across the floor toward the door, forming a lit "walkway" that leads the player's eye to the exit. Furniture clusters flank the frame left and right, framing the door between them. Camera/eye-level sits roughly at chest height with a very slight low angle, exaggerating how dark the ceiling reads.
- Visible dust motes and light shafts (god rays) through the key light are a consistent finishing touch, especially along a flashlight beam or under a ceiling bulb.

Reference images: see `docs/art-reference/` in this repo — `background_imageTwo.png`, `flashlightpic.png`, `maze_entrance_flashlight_pic.png` — the mood-board images the spec above is derived from. Re-check these directly before making any further art/lighting decisions not already covered here.

## 3. Core architecture

### RoomController / RoomDoorController / RoomStartButton
Each challenge room is a self-contained unit. Players can be inside the room before the challenge starts. Starting requires a button press (RoomStartButton) plus the required player count present — not a hold-to-confirm interact, that idea was superseded (see Section 8). Once started, the door locks (RoomDoorController) for the duration of the mini-game.

### IMiniGame interface (RoomTypes.cs / IMiniGame.cs)
Every mini-game implements a common contract so new mini-games can be added independently without touching shared systems. Each mini-game is its own self-contained prefab + script implementing this interface. Keep mini-game logic isolated — no direct references to other rooms or global game state beyond what's passed in.

### Level/Room Manager
Handles picking which subset of pre-built challenge rooms appear this run and their arrangement (randomized layer, NOT procedural geometry generation).

### Hub Threat System (HubThreatSystem.cs / ThreatIndicatorView.cs)
Shared state representing escalating hub danger while players are away solving rooms. Currently implemented as working gameplay scaffolding in plain Unity scripts (not yet networked — will convert to NetworkBehaviour/[Networked] fields once Photon Fusion is installed, see Section 9). Failing a room increases threat and respawns players to the hub (decided — see Section 8).

### Player state
Down/revive rules not yet fully specified — still open, see Section 7.

## 5. Coding conventions for every AI to follow

- Use Photon Fusion's `NetworkBehaviour` and `[Networked]` properties for anything that must be synced across clients, once Fusion is installed (door states, threat level, mini-game solved/failed state, player health/downed state). Until then, plain MonoBehaviours are fine as working scaffolding, but flag clearly in code comments what will need conversion.
- Keep mini-game scripts decoupled from room/door logic — communicate through the `IMiniGame` interface and events, not direct hard references where avoidable.
- Favor small, single-responsibility MonoBehaviours/NetworkBehaviours over large monolithic managers.
- Add brief XML doc comments (`/// <summary>`) on public methods in shared/framework scripts, since this project is being built with heavy multi-AI involvement and future context matters more than usual.
- Do not introduce HDRP-specific features, realistic PBR material workflows, or procedural dungeon generation.
- Use the project's existing `InputSystem_Actions` asset (new Input System) for any player input — do not create a second input actions asset or use the legacy Input class.
- Prefer using the MCP bridge to create/wire GameObjects and components directly in the live scene over asking the user to do it manually, and over writing throwaway custom Editor menu scripts.
- Any debug-only visual/behavior (something real players must never see) reads `HorrorGame.Core.DebugMode.IsEnabled` or subscribes to `DebugMode.Changed` — do not add a new standalone serialized bool per debug aid (see Section 8, 2026-07-20). `DebugMode` is compiled to a hardcoded-false no-op outside `UNITY_EDITOR`/`DEVELOPMENT_BUILD`, so anything gated behind it is guaranteed absent from real builds. Runtime toggle is the `K` key.

- Technical note for future work on shared-material objects: fragments all use one shared `Material` asset (`palette.Fragment`) for batching, so mutating that material directly would make every fragment glow identically instead of independently by its own distance. Used a `MaterialPropertyBlock` per-renderer instead (`Renderer.Get/SetPropertyBlock`) -- the standard Unity pattern for per-instance property overrides on a shared material, no per-fragment Material instances or draw-call-batching cost.
- Gotcha hit while verifying, worth remembering: `MaterialPropertyBlock.GetVector(id)` and `MaterialPropertyBlock.GetColor(id)` do **not** return the same numbers for a color property -- `GetVector` returns the raw linear-space-converted storage, `GetColor` converts back to the gamma-space `Color` that actually matches what you'd pass to `SetColor`. Comparing a `GetVector` read against hand-computed gamma-space expected values looks like a bug (values come back looking "squared"/too dark) but isn't one. Always verify color property blocks with `GetColor`, not `GetVector`.
- Verified live in Play mode via `execute_code` (not static inspection): at 18.9m emission was exactly `(0,0,0,0)`; moved the camera to 0.8m (inside `glowFullDistance`) and emission became exactly `(0.405, 0.270, 0.067, 0.450)` -- precisely `baseEmission (0.9, 0.6, 0.15) × 0.45`; toggled DebugMode on at 30m distance and emission was exactly the untouched full base `(0.9, 0.6, 0.15, 1.0)`, confirming distance is fully ignored in debug mode as intended.
- Single-player-only caveat flagged in code comments: distance is measured from `Camera.main`, i.e. "the" local player. Revisit once players are networked (Section 9) -- there will be multiple remote players and no single meaningful "the player" to measure from.
